# Critic fixes adopted (round 2)

The shape is right (Supabase Free plus a DIY outbox, USDA CC0 seed with IFCT held back, one pure planner) and the big platform claims checked out today: the live Supabase pausing page now says a one-year restore window, Open Food Facts product reads are 15 per minute per IP, and Firebase Spark lost Cloud Storage on 3 February 2026. But the passes contain one wrong technical premise that breaks sign-in with a hash router (supabase-js defaults to the implicit flow, not PKCE), four sync holes that can lose a gym set or a weigh-in, a storage path that the RLS policy would reject, a camera ritual the user cannot see, assisted and small-bar loads that go absurd under percentage rules, a first-time formula that disagrees with its own fixture by a third, a trend gate that hands out band verdicts from noise at the 4-day cadence, and a scope of roughly 40 evenings against a 20 target. Every item below has a fix, and the cut list keeps all six decisions at about 21 evenings.

- [Cloud: auth with the hash router] The pass says supabase-js v2 uses PKCE. The library's DEFAULT_AUTH_OPTIONS (checked today in supabase-js constants.ts) sets flowType: 'implicit'. The implicit flow returns tokens in the URL fragment (#access_token=...), which a hash router treats as a route and may rewrite before supabase-js parses it, so Google sign-in silently fails or loops on the Pages URL.
  Fix: createClient(url, key, { auth: { flowType: 'pkce', detectSessionInUrl: true, persistSession: true } }). Await getSession() (which performs the code exchange) before the router mounts, then history.replaceState to strip ?code= so the hash route stays clean. Add a Vitest-free manual check on Android Chrome, iOS Safari and both installed PWAs on evening 2, and treat an iPhone PWA failure as a gate that pulls email OTP forward.
- [Sync: dead-lettering legitimate sets] 'A 4xx moves the item to a dead state' will dead-letter real gym data: a 401 from an access token that expired during a 90-minute offline session, a 403 when the refresh raced the flush, a 429 from rate limiting. All three are 4xx. The user then sees 'N changes could not sync' with no way back, and the laptop never gets those sets.
  Fix: Classify responses: 401 and 403 refresh the session once and retry; 408, 425, 429 and 5xx retry with backoff; only 400, 409 and 422 go dead. Show dead items individually with Retry and Discard, not a count.
- [Sync: atomicity of the local write] The row write to Dexie and the outbox append are two separate writes. iOS kills backgrounded PWAs aggressively; a kill between the two leaves a completed set in Dexie with no outbox row and no dirty flag, so it never reaches the server and the other device never sees it.
  Fix: One Dexie transaction('rw', [table, outbox]) per mutation. On a server 2xx, clear dirty and delete the outbox row in one transaction keyed by outbox id. Coalesce several outbox rows for the same row id into the latest payload before sending.
- [Sync: natural unique keys versus random ids] body_weights is unique on (user_id, date_key) and photos on (user_id, date_key, pose), but ids are client-random UUIDs. Phone and laptop both record Tuesday's weight offline: the second upsert hits the unique constraint with a 409, which the design dead-letters, so one device's weigh-in is lost.
  Fix: Derive the id deterministically: uuid v5 of (user_id, date_key) for body_weights and (user_id, date_key, pose) for photos, so both devices produce the same id and the upsert merges under last-writer-wins. Keep the unique index as a belt.
- [Sync: flush mechanics on gym Wi-Fi] No request timeout and no single-flight guard: one hung POST on a captive-portal gym network blocks the queue until the tab dies, and the 'flush after every write when online' rule can start overlapping flushes. The workouts row also collides across devices (phone finishes offline while the laptop discards), and pure LWW resurrects or un-finishes it.
  Fix: Single-flight flush with an AbortController timeout of about 15 s and backoff. In the pure merge function treat finished_at and deleted_at as monotone (non-null wins over null regardless of receipt order); that is a ten-line rule and a fixture.
- [Privacy: shared devices and caches] Dexie, the outbox, cached thumbnails and the service worker cache are not namespaced by user. Friend B signing in on A's laptop sees A's rows, A's outbox pushes under B's token (403 storms), and signed-URL photo responses can persist in the Cache API after sign-out if the PWA runtime-caches supabase.co.
  Fix: Name the Dexie database gym_<user_id>; on sign-out close and delete it and the thumb store; in vite-plugin-pwa runtimeCaching exclude *.supabase.co/storage/* and /auth/* from every cache; add queryParams: { prompt: 'select_account' } on the Google call so a friend can switch accounts.
- [Privacy: first-workout install gap] Round 1 shows the install banner only after the first finished workout. On iOS the installed PWA has separate storage from Safari, so if that first workout has not flushed before the user installs, the PWA opens empty and the Safari copy's outbox never flushes unless Safari is reopened.
  Fix: Flush and show 'synced' before the install banner is allowed to appear; the PWA pulls on first open. Same rule before sign-out.
- [Photos: path and sizes disagree across passes] The cloud pass stores photos at <user_id>/<date_key>/<pose>.jpg and the storage RLS requires folder 1 to equal auth.uid(). The programming pass stores under checkins/{date}/{pose}, which that policy rejects with 403 on every upload. Thumbnails are 320 px in one pass and 240 px in the other; full-size estimates differ too.
  Fix: One constant in the domain module: `${uid}/checkins/${date}/${pose}.jpg` and `_thumb.jpg`, thumb 320 px at q0.7, full 1080 px long edge at q0.8. The migrations folder is the only schema; reconcile foods/per_100g versus food/n plus portion, favourite and recipe, food_logs versus food_log, and give the generic syncTable a per-table owner column (profiles uses id, not user_id).
- [Photos: the ritual cannot be seen] 'Rear camera preferred, phone at chest height about 2 m away' and 'a ghost of the last photo at 35 percent opacity over the preview so stance matches' contradict each other: from 2 m away the user cannot see a rear-camera preview, so the ghost overlay, the pose guide and the 3-second countdown are invisible exactly when they matter.
  Fix: Default to the front camera with a mirrored preview and un-mirror on save so left and right stay true across time; rear camera only as an option when someone else shoots. For v1 ship the file-input path (capture=user) with the ghost beside the shutter, and add the getUserMedia live overlay in v1.1 once the iPhone PWA camera is proven.
- [Free tier: keepalive at the margin] The pause rule is 'insufficient user database activity over the past week' and the doc's own yardstick is a few requests to the database each day. A GET on a one-row table every 3 days from a GitHub cron that is itself disabled after 60 days without commits is the weakest possible insurance.
  Fix: Ping daily, make it an RPC that writes (update keepalive set hit_at = now()) so it is unambiguous database activity, and add cron-job.org as a second leg from day one since it needs no commits. Keep the project owner email in the user's inbox for the warning mail.
- [Free tier: unverifiable and self-contradicting dates] The Data API grant change is dated 30 May 2026 in the schema section and 30 October 2026 (a future date) in the risks; the 3 June 2026 email-template restriction is uncited. I could not verify either today, and OTP planning hangs on the second.
  Fix: Adopt 'grant to authenticated explicitly, nothing to anon' as the rule regardless of date (harmless on older projects). Do not assume templates are editable; check in the dashboard on evening 1 and, if OTP is ever needed, configure Brevo SMTP first and then edit the template.
- [Nutrition: live USDA search is a whole evening for 30 foods] The Edge Function exists only to hide FDC_API_KEY for live search, yet the user's named staples are about 30 generic foods and the catalogue is cache-first anyway. It adds a secret, a deploy step, a function runtime and a failure mode to v1.
  Fix: No live USDA search in v1. Commit a 120 to 150 food SR Legacy seed (CC0) generated once by the laptop script, including cooked twins, and route everything else through the label form. Add the Edge Function later, when a friend's search misses twice.
- [Nutrition: Open Food Facts from the browser] The 'mandatory custom User-Agent' cannot be set from browser fetch on Safari (every iPhone) or Firefox; only Chromium honours it. So the browser path runs under the generic UA that OFF asks you not to use, and OFF rows carry ODbL share-alike obligations the friends-only app must then track and export.
  Fix: Defer OFF to post-v1. When added, go through the Edge Function (which can set the UA) with a per-user token bucket under 15 product reads per minute, or accept the browser UA and keep reads to explicit taps. The label form covers Pintola and Isopure in v1.
- [Micronutrients: the panel can never be full] 'SR Legacy has everything except iodine' is overstated per food: goat meat, several fish and some legumes lack vitamin D, E or K rows, Foundation entries often carry no vitamins at all, and no source has iodine. With iodine on the fixed 30-id list, panel = full is unreachable for every food and the coverage line never reads 100 percent.
  Fix: Define the panel over 29 ids; track iodine as a separate estimated row credited from logged salt (Indian iodised salt is 15 to 30 ppm at retail, so 5 g gives about 75 to 150 mcg). Expect a quarter of seed rows to carry 2 to 5 nulls and print that on the row.
- [Micronutrients: niacin reads low for the exact users] USDA id 1167 is preformed niacin in mg; the bar is labelled niacin equivalents. NE includes tryptophan conversion (60 mg tryptophan = 1 mg NE). On a 180 g protein recomp diet tryptophan alone supplies roughly 30 mg NE, so a bar built from 1167 shows niacin below EAR for people who are nowhere near low.
  Fix: NE = niacin_mg + tryptophan_mg / 60 using USDA id 1210 (tryptophan, present on SR Legacy); label the bar 'niacin equivalents'; label foods without tryptophan show preformed niacin with a note.
- [Micronutrients: the generic fill scaling is arbitrary] Copying peanut-butter vitamins into Pintola 'scaled by the label's protein ratio' has no basis: vitamin E and magnesium track fat and whole-peanut mass, not protein. The result is a number that looks measured and is not.
  Fix: Copy the generic's per-100 g values unscaled (same food, same density), flag estimated, never fill a whey product, and show the source line on the row.
- [Nutrition: catalogue search contradicts offline-first] pg_trgm search through PostgREST needs an RPC and a network round trip, while the cloud pass says the UI reads only Dexie and the gym has no signal. Two code paths for the same list.
  Fix: Pull the catalogue (seed plus the user's own rows) into Dexie through the same sync layer in a 'shared' mode (filter created_by is null or is_public, no user_id filter, read-only) and search client-side over a tokenised index; no trgm and no RPC in v1.
- [Programming: assisted loads under percentage rules] 'Assisted: negative allowed' breaks every rule that multiplies: a ramp at 50 percent of minus 20 kg is minus 10 kg, which is less assistance and harder than the working set; the 10 percent regression also reduces assistance and makes the set harder; e1RM is meaningless.
  Fix: Model assistance as a positive assist_g on its own axis. Progression removes one stack step of assistance, regression adds one, ramps use more assistance (assist x 1.5, rounded to the stack) or are skipped, and assisted exercises are excluded from e1RM and key-lift signals.
- [Programming: bar floors and degenerate ramps] 'Never below the empty bar' assumes a 20 kg Olympic bar. Curls and skull-crushers at Anytime Fitness use a 10 kg EZ bar or fixed bars, so a beginner's first curl (0.30 x 60 kg bench x 0.90 = 16 kg) rounds down to 15 and then floors up to 20 kg. Ramps can also round to 0 (machine at 5 kg with a 5 kg step, 50 percent, lower on tie) or to the working load itself, and a regression that rounds back to the same load loops forever.
  Fix: Bar type per exercise in the equipment profile (Olympic 20 kg, EZ 10 kg, fixed bars 10 to 50 kg by 2.5) with a floor per bar. Drop any ramp whose rounded load is at or below the previous ramp or at or above the working load. When a regression rounds to the same load, cut the rep target to lo minus 2 or offer a variation instead of counting another failure.
- [Programming: first-time formula versus its own fixture] The text applies reverse Epley at target reps plus 2, then 0.90. The worked example and the Vitest fixture (bench 85 x 6 gives incline DB 27.5 per hand) skip reverse Epley; with it the answer is about 20 kg. The two readings differ by a third, and the one the fixture pins is the one the prose does not describe.
  Fix: Declare the ratios working-load ratios (27.5 for 8 to 12 reps at that bench is the sensible value), delete the reverse Epley step from the prose, keep 0.90 and round-down, and pin the fixture to that.
- [Programming: deload trigger C and heavy ramp singles] Offering a deload after two weeks under 50 percent attendance prescribes rest to someone who has been resting. Separately, 85 percent and 92 percent singles in every ramp above 60 kg add fatigue before 8 to 12 rep work for no benefit.
  Fix: Replace trigger C with the existing 'first session back, loads minus 5 percent' rule. Use the 85 percent single only when working reps are 8 or fewer and the 92 percent single only for 5 or fewer; otherwise end the ramp at 70 percent x3.
- [Programming: custom builder count table versus its own estimate] At 30 minutes the table demands 3 exercises with 2 compounds; each compound with ramps and 150 s rests costs 12 to 15 minutes by the pass's own estimator, so most 30 and many 45 minute requests return needsMinutes instead of a plan, which is the one case the user explicitly asked to be guided through.
  Fix: Fill slots until the estimate exceeds the budget rather than from a table; at 30 minutes one compound with 90 s rests plus two isolations; treat the table as a cap.
- [Programming: cardio finisher intensity] Incline walk 15 to 20 min at 10 to 12 percent and 5 to 6 km/h after push and pull sessions is about 8 to 9 METs, four times a week, and it bleeds into the next day's legs session.
  Fix: Default 6 to 8 percent at 5 km/h; keep 10 to 12 percent as the 'hard' intent option; keep the no-hard-cardio-before-legs rule.
- [Check-in maths: verdicts from noise] At 4-day spacing the Theil-Sen slope from 4 readings has a one-sigma error of sigma / (4 x sqrt 5) kg per day, which at a realistic 0.6 kg day-to-day noise is about 0.6 percent per week, wider than the entire on-track band (0.5 percent wide). Even 7 readings over 24 days give a 95 percent interval of about plus or minus 0.5 percent per week, so the 'full verdict' can sit one band off and the slow-down rule at 1.5 percent can fire falsely.
  Fix: Compute the slope's confidence interval from the readings' own residuals and issue a band verdict only when the interval lies inside one band or wholly beyond the too-fast line; otherwise show 'direction: down, not yet precise, n of 10'. Expect 10 to 12 check-ins before a band verdict at this cadence. Let extra weigh-ins between check-ins count toward the trend (the photo cadence stays at 4 days), which roughly halves the wait. Hysteresis of two check-ins is fine.
- [Check-in reminder] A subscribable .ics with INTERVAL=4 from a fixed DTSTART drifts from 'last check-in plus 4 days' the first time one is late, and GitHub Pages cannot serve a per-user feed.
  Fix: After each check-in offer a downloadable .ics containing the next 12 due dates as all-day events, or rely on the Home card alone in v1.
- [Scope] The three passes sum to about 32 evenings (8 cloud, 7 food, 17 programming) before the round-1 core (shell, session screen, library, review engine, charts, PWA) adds another 6 to 8: roughly 40 against a target of 20.
  Fix: The cut list below lands at about 21 evenings and keeps all six decisions. Order: core and cloud sync first, nothing that writes data before the sync layer is green on both devices; then program; then check-in; then food.
